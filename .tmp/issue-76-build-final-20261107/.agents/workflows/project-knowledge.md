# Project knowledge maintenance

Read the relevant entries in [tips.md](../../tips.md) and [winning-features.md](../../winning-features.md)
when starting work, alongside the current code and decision register. These files retain learning;
they do not override owner instructions, business facts or confirmed/superseding decisions.

## Owner tips

When the owner shares a tip, trick, technique or useful insight, record it promptly in tips.md, even
if it is not implemented. Save source/speaker, date, category, what was said, why it matters here,
applicability and status. Attribute external advice to its source; do not turn it into a confirmed
business fact or authorization to change the website. Label agent recommendations separately.
Check for an existing topic/source first and update or link it rather than duplicating it. Keep the
owner's interpretation and exceptions, including branch creation only on request. Put confirmed
project decisions and rejected approaches in the existing decision register and link them here.

## Winning features

Whenever work adds, changes or removes a meaningful reusable pattern, update its entry in
winning-features.md during the same task. Record:

- What the pattern currently does and where its code lives.
- Why it may help this business; distinguish design rationale from measured benefit.
- The reusable principle and constraints when adapting it elsewhere.
- Source revision, verification date, applicable checks and local/pushed/deployed status.
- Any measured result with its source/window, or explicitly no measured outcome.

Verify the actual code before claiming a pattern exists. A seed copied from another site is a proposal
until checked here. Do not import another business's services, prices, warranties, photos, reviews or
performance claims. Keep implementation, browser verification and measured conversion/SEO results
separate. Do not invent ranking gains, conversion lift, review eligibility or universal guarantees.
When a pattern is removed or superseded, mark the old entry retired/superseded with its reason and
replacement; do not leave it described as current or discard a useful rejection.

## Checkpoint and concurrency

Before writing either file, re-read the relevant entry and current diff so concurrent additions are
preserved. Use descriptive headings and source references; do not rely on a globally unique numeric
ID without checking it. Capture useful insights at milestones and confirm the files are current at
sunset. Skip an empty update when nothing relevant changed. In a read-only task, record useful advice
only within the authorized note-taking scope; do not imply application code was changed.

Keep records concise and specific. If code, evidence or source is unavailable, mark the claim unknown
and name the missing check. Published GitHub records enable another session to reuse the learning;
unpublished local entries must be identified in the handoff. Never store credentials or private
customer records in these files.
